# Message / API Contract Specification

All inter-agent communication uses one shared Pydantic message envelope,
defined once in [`shared/schema.py`](shared/schema.py) and imported by
every service (`sys.path` is adjusted so each container can `from shared.schema
import AgentMessage, AgentResponse, ...`). This is the single source of
truth — this document describes it, it does not redefine it.

## `AgentMessage` (request envelope)

Sent by the Coordinator to an agent's `POST /invoke`, and also used
internally for approval-execution dispatches.

```json
{
  "incident_id": "OEM-INC-2025-017",
  "task_id": "TASK-TRACE-004",
  "correlation_id": "CORR-7781",
  "sender": "coordinator-agent",
  "recipient": "traceability-agent",
  "action": "identify_suspect_population",
  "payload": { "...": "..." },
  "requested_by": "quality-manager",
  "timestamp": "2025-05-15T09:30:00Z",
  "attempt": 1,
  "max_attempts": 3
}
```

| Field | Type | Notes |
|---|---|---|
| `incident_id` | str | Generated by the Coordinator per complaint (`OEM-INC-XXXXXXXX`). |
| `task_id` | str | Auto-generated UUID-based id per dispatch (`TASK-XXXXXXXX`) if not supplied. Used for the duplicate-message guard (§ below). |
| `correlation_id` | str | Generated once per incident (`CORR-XXXXXXXX`), threaded through every message and audit-log row for that incident's entire lifecycle. |
| `sender` / `recipient` | str | One of the `AgentName` values (see below). |
| `action` | str | Must be one of the recipient's valid actions (see table below). |
| `payload` | dict | Action-specific request body — see per-agent payload shapes below. |
| `requested_by` | str | Human identity that ultimately authorized this workflow (e.g. `"quality-manager"`). |
| `timestamp` | str | ISO-8601 UTC, auto-set. |
| `attempt` / `max_attempts` | int | Set by the shared HTTP client (`shared/http_client.py`) on each retry; downstream agents use `task_id` (not `attempt`) for dedup, so a retried attempt is idempotent. |

## `AgentResponse` (response envelope)

Returned by every agent's `POST /invoke`.

```json
{
  "incident_id": "OEM-INC-2025-017",
  "task_id": "TASK-TRACE-004",
  "correlation_id": "CORR-7781",
  "sender": "traceability-agent",
  "recipient": "coordinator-agent",
  "action": "identify_suspect_population",
  "status": "ok",
  "result": { "...": "..." },
  "error": null,
  "timestamp": "2025-05-15T09:30:01Z",
  "duration_ms": 42.7
}
```

| Field | Type | Notes |
|---|---|---|
| `status` | `ActionStatus` | See enum values below. |
| `result` | dict | Action-specific response body. |
| `error` | str \| null | Populated on `error` / `timeout` / `unavailable`. |
| `duration_ms` | float | Round-trip time as measured by the caller. |

### `ActionStatus` values

`pending`, `ok`, `error`, `timeout`, `unavailable`, `awaiting_approval`,
`approved`, `rejected`, `executed`.

`timeout` / `unavailable` / `error` are all treated identically by the
Coordinator's orchestration: the workflow continues and that agent's
findings are marked unavailable, per the resilience requirement.

## Valid `action` values per agent

| Agent | Action | Payload (request) | Result (response) shape |
|---|---|---|---|
| `quality-rag-agent` | `retrieve_requirements` | `{query, symptom?, top_k?}` | `{query, evidence[], pfmea_control_plan_findings[], interpretation, confidence, no_evidence_found}` |
| `traceability-agent` | `identify_suspect_population` | `{part_number?, date_range_start?, date_range_end?}` | `{date_range_used, total_units_in_range, overall_bad_rate, segment_analysis[], firmware_analysis[], disproportionate_segment_found, suspect_population, common_factor, recommended_containment_boundary, reasoning}` |
| `process-maintenance-agent` | `analyze_process_deviations` | `{date_range_start?, date_range_end?, line?, shift?, connector_lot?}` | `{units_analyzed, deviations[], diagnostic_recommendations[], proposed_work_order}` |
| `process-maintenance-agent` | `execute_work_order` | `{work_order_id, approved}` | `{work_order_id, status, work_order?}` |
| `logistics-agent` | `assess_containment` | `{part_number?, suspect_serial_numbers?[], suspect_count?, containment_boundary_description?}` | `{suspect_count_total, affected_by_location, proposed_actions[]}` |
| `logistics-agent` | `execute_containment_action` | `{action_id, approved}` | `{action_id, status, command?}` |
| `logistics-agent` | `release_containment_action` | `{action_id, approved}` | `{action_id, status, command?}` -- releases a command that previously reached `executed` back to `released`; errors if the target command was never executed. |

Coordinator-native pseudo-actions (`oem_notification`, `8d_update`) do not
go through `/invoke` on another agent — they are proposed during
consolidation and executed directly by the Coordinator once approved,
since no dedicated OEM-communications agent exists in this system's scope
(documented as an out-of-scope simplification in `README.md`).

## Evidence vs. interpretation separation (RAG agent)

Per the take-home's requirement, `quality-rag-agent`'s result always keeps
retrieved evidence and agent-generated interpretation in separate fields:

- `evidence` / `pfmea_control_plan_findings`: raw retrieved passages only —
  `{document, section, content, relevance}`, no agent commentary blended in.
- `interpretation`: a separate LLM-generated (or rule-based fallback) prose
  field that explicitly does not appear inside `evidence`.
- `no_evidence_found: true` + `confidence: "none"` when nothing clears the
  relevance floor — the agent explicitly declines rather than asserting an
  unsupported answer.

## Duplicate-message guard

Every agent (including the Coordinator) keeps an in-memory
`TaskDedupStore` (`shared/dedup.py`) keyed by `task_id`. If a message with
a previously-seen `task_id` arrives (e.g. a retried dispatch after a
transient timeout), the agent returns the cached `AgentResponse` instead of
re-executing the action — this is what makes the Coordinator's
timeout+retry policy safe to use against non-idempotent actions like
`execute_work_order`.

## Auth

Every `/invoke` (and every other non-`/health`) endpoint requires the
`X-API-Key` header, validated by the shared `verify_api_key` FastAPI
dependency (`shared/auth.py`) against `SHARED_API_KEY`. This is explicitly
a simplified stand-in for real service-to-service auth (see README).
